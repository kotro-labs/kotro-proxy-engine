# Escape Lab Scoreboard — v2 design

**Status: design spec, not yet implemented.** This document proposes a
richer public scoreboard on top of the existing Escape Lab corpus
(`testdata/escape-lab/scenarios.json`, rendered today as
[`ESCAPE-LAB-MATRIX.md`](ESCAPE-LAB-MATRIX.md)). It does not change how CI
gates today — see "CI gate vs. public scoreboard" below for why those stay
separate.

## Why change it

The current matrix answers one question well: *"did Kotro's observed
behavior match what the corpus declared it should do?"* That's a
regression gate, and 14/14 rows matching declared behavior today is a real,
useful signal — a divergence means something changed unexpectedly.

It answers a different question badly: *"how much attack coverage does
Kotro actually have?"* A reader skimming "14/14" can walk away thinking
"14/14 attacks stopped." The real breakdown as of 2026-08-02 is 9/14
prevent-or-better, 1 observe-only, 1 mode-dial assertion (not a coverage
row), 1 not-measurable-over-HTTP, and 3 explicit `none` (known gaps with a
stated owning phase). That distinction needs its own columns, not a
footnote.

## New column schema

| Column | Meaning |
|---|---|
| **ID / Scenario** | Same as today (`EL-NN`, short name) |
| **Category** | Same as today (injection, secret-exfiltration, egress, persistence, tool-integrity, operator-control, resource-abuse, monitoring-integrity — plus new categories added below) |
| **Threat mapping** | Cross-reference to OWASP Agentic Top 10 / OWASP MCP Top 10 category where one applies (best-effort, not a compliance claim) |
| **Attempted** | Was this scenario actually run against a live proxy this cycle? (vs. `not measured` / `cli-only`) |
| **Prevented** | Outcome was `prevent` — blocked before effect |
| **Detect-only** | Outcome was `detect` or `transform` — allowed through (possibly modified) but flagged with evidence |
| **Known bypass** | Outcome was `none` **and** there's a filed, owned tracking item (not a silent gap) — links to the owning phase/issue |
| **False positive rate** | Where measurable: benign-traffic scenarios that should score `none`/pass-through but got flagged. Most current scenarios are attack-only and don't measure this yet — see "FP measurement gap" below |
| **Latency** | Same as today — full scenario duration including multi-step scenarios, so single- vs. multi-step latencies aren't directly comparable across rows |

The **prevention rate** published alongside the matrix becomes:
`prevented / attempted` and `(prevented + detect-only) / attempted`,
shown separately — never collapsed into one number, so "we detect it but
don't block it" and "we block it" stay visually distinct.

## FP measurement gap

None of the 15 current scenarios are benign-traffic controls — every row
is an attack scenario. That means the corpus currently cannot measure
false positives at all (a legitimate `git diff` containing the word
"password" as a variable name, for instance, might over-trigger
redaction, and nothing today checks for that). Adding benign-traffic
counterpart scenarios per category is part of the expansion below, not an
afterthought.

## CI gate vs. public scoreboard

These stay **two different artifacts**, deliberately:

- **CI gate** (`scripts/escape-lab.py`, no `--allow-divergence`): fails
  the build if observed behavior diverges from *declared* behavior for
  any row, including `none` rows — a `none` scenario that starts
  returning `prevent` unexpectedly is just as much a regression as the
  reverse, because it means something changed that wasn't intentional.
  This must stay strict and boring.
- **Public scoreboard** (this design): reports prevention/detection/
  bypass rates for human consumption. It can change in presentation
  (new columns, a rendered dashboard, category rollups) without ever
  weakening the CI gate underneath it. The gate is the regression proof;
  the scoreboard is the honesty layer on top of it.

## Implementation notes (not yet built)

- `scripts/escape-lab.py` would need a `--scoreboard` render mode
  producing the table above from live run output, separate from
  `render_markdown()`'s existing declared-vs-observed table.
- Prevention-rate rollups should be computed per category as well as
  overall, so a reader can see "egress: 0% prevented, 2 known bypass"
  distinctly from the aggregate number.
- This is a **P1** item (`CONSOLIDATED-NEXT-STEPS.md` §5, item 1.7) —
  scoped as its own follow-up PR, not bundled into the scenario
  expansion itself, so the rendering change and the new scenarios can be
  reviewed independently.
